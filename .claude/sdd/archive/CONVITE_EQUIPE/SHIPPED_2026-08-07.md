## Summary

O sócio agora traz gente nova para a equipe por um **link compartilhável**: escolhe o papel (funcionário ou sócio), gera o link, e quem abre se cadastra (ou entra, se já tem conta) e fica **pendente** até o responsável **aprovar**. O pendente não aparece nem atua na equipe enquanto não for aprovado — e isso saiu de graça: o convite aceito vive numa tabela `invite` própria (nunca em `workspace_members`), então `is_workspace_member` continua `false` sem tocar em nenhuma policy já shipada. A `invite` é service-role only (RLS ligada, zero policies): o token é a credencial, nenhum cliente lê a tabela. O convite-por-e-mail antigo (`convidarMembroAction`) permaneceu como atalho para usuários já existentes. Esta é a feature que passou a **criar contas `funcionario`** — antes o cadastro só fazia admin/ajudante.

## Lessons Learned

### Process

- **O convite já existia pela metade.** `convidarMembroAction` adicionava usuário existente, direto, sem aprovação. Ler isso antes cedo virou o escopo em *adicionar link + aprovação ao lado*, mantendo o fluxo antigo como atalho — em vez de reescrever onboarding.
- **Rastrear o cadastro revelou o verdadeiro entregável:** esta é a feature que passou a criar contas `funcionario`. O convite não é só um add — é o *mecanismo* que cria a conta com o papel certo. Isso só ficou claro seguindo o `cadastrarAction` até o fim.

### Technical

- **Invisibilidade do pendente saiu de graça.** A decisão de deixar o aceito no `invite` (e não em `workspace_members`) significa que `is_workspace_member` retorna `false` sem nenhuma policy nova — a engrenagem de membership endurecida no CHAT_E_PERMISSOES ficou intocada. Menos código *e* menos superfície de RLS.
- **Tabela service-role only (RLS on, zero policies) = o token é a credencial.** Nenhum cliente lê a `invite`; todo aceite/aprovação passa pelo servidor via admin client. O preview público lê pelo token via admin, não por policy. Provado por 1 teste de integração no banco real.
- **`podeAceitar` como função pura** rendeu o teste-âncora de expiração (4 casos), rápido e sem DB — mesmo padrão do `diasEmConflito` da agenda.

### Communication

- **O mapeamento papel-do-convite ↔ `tipo_base`** (owner→`admin`, membro→`funcionario`) foi levantado como Open Question no DEFINE e fechado na Decision 3 do DESIGN **antes** do código — evitou retrabalho no `cadastrarAction` e no schema de validação.

### Tools & Libraries

- **vitest sem alias `@/` (de novo):** o teste unit nasceu com import relativo (`../lib/convite-status`) desde o começo, aplicando a lição da agenda em vez de tropeçar nela.
- **Conector MCP** aplicou a migration aditiva `0016` e os advisors — o único novo é INFO `rls_enabled_no_policy` na `invite`, que **é** o design (service-role only), não um alerta. Reconhecer isso evitou "consertar" o que era intencional.

## Recommendations for Future Work

| Area | Recommendation |
|------|----------------|
| Verificação | Fluxo completo com conta **real** (não-demo, que é read-only): gerar → cadastrar pelo link → aprovar → confirmar entrada em `workspace_members` |
| Revogar link (YAGNI) | Expirar/revogar um convite manualmente na tela da equipe, se o link vazar antes do uso |
| Reuso do link | Hoje é single-use (pendente→aceito). Se precisar de link de time reutilizável, um `max_usos` na `invite` |
| Visibilidade | Mostrar convites **pendentes ainda não aceitos** (e o tempo até expirar) na `/equipe`, não só os que já foram aceitos |
